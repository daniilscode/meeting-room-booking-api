# Meet Reserve

Meet Reserve — REST API для бронирования переговорных комнат.

Проект моделирует сценарий: пользователь выбирает комнату и временной интервал, создаёт временную бронь, подтверждает её или отменяет. Система предотвращает пересечение активных бронирований и автоматически освобождает просроченные временные брони.

## Возможности

- создание и деактивация переговорных комнат;
- просмотр всех комнат или только активных;
- создание временной брони со статусом `PENDING`;
- подтверждение и отмена брони;
- автоматическое истечение неподтверждённых броней;
- запрет бронирования неактивной комнаты;
- защита от пересекающихся бронирований;
- единый формат ошибок API;
- OpenAPI-спецификация и Swagger UI;
- unit-тесты и интеграционный тест конкурентного бронирования.

## Бизнес-правила бронирования

- Новая бронь создаётся со статусом `PENDING` и должна быть подтверждена за 10 минут.
- Длительность бронирования — от 15 минут до 4 часов.
- Начало бронирования должно быть в будущем.
- Для одной комнаты нельзя создать пересекающиеся активные брони.
- Активными считаются брони со статусами `PENDING` и `CONFIRMED`.
- Бронь `CANCELLED` или `EXPIRED` больше не блокирует интервал.
- Неактивную комнату нельзя забронировать.

## API

Swagger UI: `http://localhost:8080/swagger-ui/index.html`

OpenAPI-описание: `openapi/openapi.yaml`.

| Метод | Endpoint | Назначение |
|---|---|---|
| `POST` | `/api/v1/rooms` | создать комнату |
| `GET` | `/api/v1/rooms` | получить список комнат |
| `GET` | `/api/v1/rooms/{id}` | получить комнату |
| `POST` | `/api/v1/rooms/{id}/deactivate` | деактивировать комнату |
| `POST` | `/api/v1/bookings` | создать временную бронь |
| `POST` | `/api/v1/bookings/{id}/confirm` | подтвердить бронь |
| `DELETE` | `/api/v1/bookings/{id}` | отменить бронь |

## Сценарий в Postman

### 1. Создать комнату

Создайте запрос `POST http://localhost:8080/api/v1/rooms`.

```json
{
    "name": "Переговорная Alpha",
    "capacity": 8,
    "hasProjector": true
}
```

Ожидаемый результат — `201 Created`. Сохраните значение `id` из ответа: оно понадобится для создания брони.

### 2. Создать временную бронь

Создайте запрос `POST http://localhost:8080/api/v1/bookings`.

Значение `roomId` замените на `id` комнаты из предыдущего ответа. Время начала должно быть в будущем:

```json
{
    "roomId": 1,
    "userId": 42,
    "title": "Архитектурный комитет",
    "startTime": "2026-12-01T10:00:00Z",
    "endTime": "2026-12-01T11:00:00Z"
}
```

Ожидаемый результат — `201 Created`, статус брони — `PENDING`. Сохраните `id` брони из ответа.

### 3. Подтвердить бронь

Создайте запрос `POST http://localhost:8080/api/v1/bookings/{bookingId}/confirm`, где `{bookingId}` — UUID брони из предыдущего ответа.

Ожидаемый результат — `200 OK`, статус брони изменится на `CONFIRMED`.

### 4. Проверить защиту от пересечения

Повторите запрос создания брони из шага 2 с тем же `roomId`, `startTime` и `endTime`.

Ожидаемый результат — `409 Conflict`: выбранный интервал уже занят.

### 5. Отменить бронь

Создайте запрос `DELETE {{baseUrl}}/api/v1/bookings/{bookingId}`.

Ожидаемый результат — `204 No Content`. После отмены этот временной интервал снова можно забронировать.


## Надёжность при параллельных запросах

При создании брони используется Redis lock на комнату. Окончательная гарантия целостности находится в PostgreSQL: база содержит `EXCLUDE USING gist` constraint, который запрещает пересечение активных интервалов одной комнаты. Поэтому при гонке запросов только одна бронь может занять интервал.


Тест проверяет, что при 20 одновременных запросах на один интервал только один создаёт бронь, а остальные получают конфликт.
