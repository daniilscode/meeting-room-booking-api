# Задача 2. Жизненный цикл брони

## Цель

Завершить сценарий, начатый в задаче 1: временную бронь `PENDING` можно подтвердить или отменить. Если её не подтвердили за 10 минут, она переходит в `EXPIRED`, а интервал снова становится доступен.

Результат задачи — два REST endpoint, фоновая очистка просроченных броней и тесты переходов статусов. Использовать существующие `Booking`, `BookingStatus`, `BookingRepository`, `Clock`, OpenAPI-контракт и единый формат ошибок.

## Текущее состояние и границы задачи

- `POST /api/v1/bookings` уже создаёт `PENDING` с `expiresAt = createdAt + 10 минут`.
- В PostgreSQL действует ограничение, запрещающее пересечение `PENDING` и `CONFIRMED` для одной комнаты.
- В `BookingRepository` уже есть запрос `expireOverdueBookings(...)`, который вызывается при создании новой брони. Фоновая задача должна использовать ту же семантику истечения.
- Аутентификации пока нет. В этой задаче не добавлять параметр `userId` для подтверждения или отмены: присланный клиентом ID не доказывает владение бронью. Проверку владельца добавить после внедрения Spring Security.
- Управление комнатами и поиск свободных комнат относятся к следующим задачам.

## Модель состояний

```text
PENDING ──confirm до expiresAt──▶ CONFIRMED
   │
   ├──cancel────────────────────▶ CANCELLED
   │
   └──now >= expiresAt─────────▶ EXPIRED

CONFIRMED ──cancel──────────────▶ CANCELLED
```

Правила:

1. Срок истекает в момент `now >= expiresAt`. Ровно в `expiresAt` подтверждать уже нельзя.
2. После подтверждения установить `expiresAt = null`: срок временного удержания больше не действует.
3. После отмены установить `expiresAt = null`. Для `EXPIRED` сохранить исходное `expiresAt` для истории.
4. `CONFIRMED`, `CANCELLED` и `EXPIRED` не переходят обратно в `PENDING`.
5. Повторное подтверждение `CONFIRMED` возвращает текущую бронь с `200 OK`; повторная отмена `CANCELLED` возвращает `204 No Content`.
6. Подтверждение `CANCELLED` возвращает `409 BOOKING_NOT_PENDING`; подтверждение или отмена `EXPIRED` возвращает `410 BOOKING_EXPIRED`.
7. Отмена `PENDING`, у которой уже наступил `expiresAt`, сначала фиксирует `EXPIRED`, затем возвращает `410 BOOKING_EXPIRED`.

## REST API

Все ответы со временем возвращаются в UTC в формате ISO 8601. UUID в пути должен быть корректным; неверный UUID возвращает `400 VALIDATION_ERROR`.

### Подтверждение

`POST /api/v1/bookings/{id}/confirm`

Тело запроса отсутствует. Успех — `200 OK` с существующим `BookingResponse`:

```json
{
  "id": "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11",
  "roomId": 1,
  "userId": 42,
  "title": "Архитектурный комитет",
  "startTime": "2026-11-01T14:00:00Z",
  "endTime": "2026-11-01T15:00:00Z",
  "status": "CONFIRMED",
  "expiresAt": null,
  "createdAt": "2026-11-01T13:00:00Z"
}
```

### Отмена

`DELETE /api/v1/bookings/{id}`

Успех — `204 No Content`, без тела. Запись не удаляется из базы: её статус становится `CANCELLED`. После commit другой запрос может занять освободившийся интервал.

### Ошибки

| Ситуация | HTTP | `code` |
|---|---:|---|
| Неверный UUID в пути | 400 | `VALIDATION_ERROR` |
| Бронь не найдена | 404 | `BOOKING_NOT_FOUND` |
| Подтверждение отменённой брони | 409 | `BOOKING_NOT_PENDING` |
| Подтверждение или отмена истёкшей брони | 410 | `BOOKING_EXPIRED` |

Для ошибок использовать текущий `ErrorResponse` с полями `code`, `message`, `timestamp`. Добавить нужные ответы в `openapi/openapi.yaml` и обработчики в `GlobalExceptionHandler`.

## Транзакции и конкурентный доступ

Переход статуса должен быть атомарным и проверять исходный статус непосредственно в SQL. Рекомендуемый способ — условный `UPDATE ... WHERE id = :id AND status = :expectedStatus ...` с проверкой числа обновлённых строк. Альтернатива — блокировка строки `SELECT ... FOR UPDATE` внутри транзакции. Простая последовательность `findById()` → проверка Java-поля → `save()` без блокировки не подходит: подтверждение, отмена и scheduler могут одновременно прочитать `PENDING`.

Для подтверждения условие обновления должно включать `expires_at > :now`. Если обновлено 0 строк, повторно прочитать бронь и различить `404`, уже подтверждённую, отменённую и истёкшую. Если срок истёк, перевести `PENDING` в `EXPIRED` и **зафиксировать это изменение до возврата `410`**. Исключение, выброшенное из той же `@Transactional`-операции, откатит переход в `EXPIRED`; этот случай нужно обработать отдельной транзакцией либо вернуть результат из транзакции и сформировать ошибку после её завершения.

Для отмены также проверять актуальное состояние под блокировкой или условным обновлением. Если два запроса одновременно подтверждают и отменяют одну бронь, после завершения обоих её конечное состояние должно соответствовать одному допустимому последовательному порядку: `CANCELLED` либо `CONFIRMED` с последующей отменой. Истёкшая бронь не может стать `CONFIRMED`.

Redis-lock из создания брони можно переиспользовать как оптимизацию, но корректность переходов должна обеспечиваться PostgreSQL. Не держать Redis-lock после ответа, если транзакция ещё не завершилась.

## Фоновое истечение

Добавить scheduler с запуском примерно раз в минуту. Он одним запросом переводит все `PENDING`, у которых `expires_at <= clock.instant()`, в `EXPIRED`. Включить планировщик через Spring. Запрос должен обновлять только `PENDING`, чтобы не затронуть подтверждённые и отменённые брони.

Истечение при обращении к конкретной брони проверять сразу, не ожидая scheduler. Аналогично создание новой брони не должно отклоняться только потому, что scheduler ещё не обработал старый `PENDING`.

Использовать внедрённый `Clock`, чтобы время в сервисе и тестах было управляемым. Ошибка одного запуска scheduler не должна останавливать последующие запуски; записывать количество обновлённых броней в лог.

## Изменения в коде

1. Расширить `openapi/openapi.yaml` двумя endpoint и их ответами; сгенерированные Java-файлы вручную не редактировать.
2. Расширить `BookingService` методами подтверждения и отмены.
3. Добавить в `BookingRepository` атомарные запросы перехода статусов и чтение, необходимое для определения результата.
4. Реализовать переходы в сервисе и преобразование `Booking` в общий `BookingResponse`.
5. Добавить scheduler и включить scheduling.
6. Добавить исключения и HTTP-маппинг в `GlobalExceptionHandler`.
7. Если потребуется изменение схемы, создать новую миграцию `003-...`; не редактировать уже применённые миграции `001` и `002`.

## Критерии готовности

- `PENDING` до истечения подтверждается и возвращает `CONFIRMED` с `expiresAt: null`.
- Подтверждение ровно в `expiresAt` и позже возвращает `410`, а в базе остаётся `EXPIRED`.
- `PENDING` и `CONFIRMED` отменяются с `204`; после отмены интервал можно забронировать снова.
- Повторное подтверждение `CONFIRMED` и повторная отмена `CANCELLED` идемпотентны.
- Неизвестный ID, неверный UUID и недопустимые переходы возвращают оговорённые коды и единый JSON.
- Scheduler переводит только просроченные `PENDING`; повторный запуск не меняет результат.
- Одновременные confirm, cancel и scheduler не приводят к недопустимому статусу.
- `./gradlew test` проходит; API проверено с PostgreSQL и Redis через интеграционные тесты.

## Минимальный набор тестов

1. Подтверждение действующей `PENDING`-брони, включая `expiresAt: null`.
2. Подтверждение за мгновение до `expiresAt` и ровно в `expiresAt`.
3. Повторное подтверждение `CONFIRMED`.
4. Отмена `PENDING`, отмена `CONFIRMED`, повторная отмена `CANCELLED`.
5. Ошибки для отсутствующей, отменённой и истёкшей брони.
6. Scheduler обрабатывает только просроченные `PENDING` и безопасен при повторном запуске.
7. Интеграционный тест с PostgreSQL: два одновременных перехода одной брони не создают недопустимого состояния.
8. HTTP-тесты подтверждают статусы ответов и формат `ErrorResponse`.

Для интеграционных тестов использовать Testcontainers с PostgreSQL и Redis. Время задавать через фиксированный `Clock`; не строить проверки на `Thread.sleep()`.
